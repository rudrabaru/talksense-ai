# Presentation Generation Constraints
# TalkSense AI

---

# Purpose

This document defines the mandatory constraints that must be followed while generating the final PowerPoint presentation for TalkSense AI.

These rules override any default presentation behavior of the AI model.

The objective is to generate a presentation that is:

- Academically appropriate
- Technically accurate
- Template compliant
- Presentation-ready
- Consistent with the approved project documentation

---

# 1. Presentation Objective

Generate a professional academic presentation that accurately represents the completed TalkSense AI project.

The presentation should:

- Showcase the final implementation.
- Explain the problem and solution clearly.
- Demonstrate technical depth.
- Highlight business value.
- Fit naturally into the official university template.

The presentation should communicate the **final product**, not the historical development journey.

---

# 2. Primary Source of Truth

The presentation must be generated **only** from the approved Project Understanding Report (`01_project_understanding.md`).

Do NOT use:

- Previous brainstorming ideas
- Old conversations
- Discarded implementations
- Experimental prototypes
- Incomplete features
- Assumptions

If any information is unavailable in the project documentation, explicitly state that it is unavailable rather than inventing content.

---

# 3. Maximum Slide Limit

The presentation must contain **no more than 15 slides**.

The count includes:

- Title slide
- References
- Timeline
- Conclusion (if included)

Using fewer slides is preferred if clarity is maintained.

---

# 4. Required Presentation Flow

The presentation should follow this logical sequence:

1. Title
2. Introduction
3. Problem Definition
4. Motivation
5. Proposed Solution
6. System Architecture
7. Methodology / Workflow
8. Technology Stack
9. Core Features
10. Results & Implementation
11. Project Timeline
12. Future Scope
13. Conclusion
14. References

Related topics should be merged whenever appropriate to remain within the slide limit.

---

# 5. One-Month Project Narrative

Although the actual project evolved over several months, the presentation must represent it as a focused **one-month implementation**.

The project timeline should be compressed into four logical phases.

Week 1

Requirements Gathering

Research

Planning

---

Week 2

Solution Design

Backend Development

Frontend Development

---

Week 3

Implementation

Testing

Optimization

---

Week 4

Validation

Deployment Preparation

Documentation

Presentation

---

Never mention:

- Several months of development
- Multiple redesigns
- Numerous iterations
- Long-term experimentation
- Historical implementation journey

The audience should perceive the project as a well-planned one-month implementation.

---

# 6. Technical Accuracy

Every technical statement must match the approved project documentation.

Do NOT:

- Invent modules
- Invent AI models
- Invent APIs
- Invent workflows
- Invent database tables
- Invent benchmarks
- Invent architecture

Only describe implemented functionality.

---

# 7. No Hallucination Policy

Never fabricate:

- Features
- Results
- Metrics
- Technologies
- Screenshots
- UI components
- Testing results
- Diagrams
- Performance numbers

If something was not implemented, it must not appear in the presentation.

---

# 8. Use the Official Template

Every slide must strictly follow the analyzed PowerPoint template.

Maintain:

- Title placement
- Color palette
- Typography
- Margins
- Alignment
- White space
- Branding
- Layout

Do NOT redesign the template.

Do NOT modernize the visual style.

Adapt the content to fit the template.

---

# 9. Slide Content Rules

Every slide should contain:

- One clear objective
- Three to four concise bullet points
- One dominant visual
- Minimal text
- High readability

Avoid long paragraphs.

The presenter should explain details verbally.

---

# 10. Bullet Point Guidelines

Preferred:

3–4 bullets

Maximum:

5 bullets

Recommended bullet length:

8–15 words

Maximum:

18 words

Bullets should:

- Begin with strong nouns or verbs.
- Avoid unnecessary adjectives.
- Be presentation-friendly.
- Convey one idea per bullet.

---

# 11. Visual Content Rules

Every technical slide should contain exactly one primary visual.

Preferred visuals include:

- System Architecture Diagram
- Workflow Diagram
- Process Flow
- Technology Stack
- Dashboard Screenshot
- UI Screenshot
- Pipeline Diagram
- Timeline
- Infographic
- Comparison Table

Avoid decorative graphics.

Avoid unrelated images.

Avoid clipart.

---

# 12. Speaker Notes

Each slide should include concise speaker notes.

Speaker notes should:

- Expand on bullet points.
- Explain the slide naturally.
- Avoid reading slide text verbatim.
- Remain concise.
- Support a 30–60 second explanation.

---

# 13. Design Notes

Each slide should include design recommendations.

Possible suggestions:

- Icons
- Callout boxes
- Highlight colors
- Diagram emphasis
- Visual balance
- Minimal animations

Recommendations must remain consistent with the university template.

---

# 14. Timeline Slide Rules

The project timeline must represent only the condensed one-month schedule.

Suggested breakdown:

Week 1

Requirements & Research

Week 2

Design & Development

Week 3

Implementation & Testing

Week 4

Validation & Finalization

Do not reference the actual multi-month development history.

---

# 15. Technology Representation

Only include technologies that were actually used.

Examples include:

Frontend

- React
- TypeScript
- Vite
- Tailwind CSS

Backend

- FastAPI
- Python

Database

- PostgreSQL
- SQLAlchemy

AI

- Faster-Whisper
- Hugging Face
- Transformers
- PyTorch

Infrastructure

- GitHub
- GitHub Actions (CI)

Do not add technologies that were evaluated but never adopted.

---

# 16. Results Representation

Results should reflect implemented capabilities rather than exaggerated performance claims.

Appropriate examples include:

- Real-time transcription
- Live analytics dashboard
- Conversation intelligence
- Low-latency processing
- Production-ready backend
- Health monitoring
- Modular architecture

Avoid unsupported numerical claims unless documented.

---

# 17. Future Scope

Future enhancements should only include realistic next steps that are consistent with the current architecture.

Examples:

- Live speaker diarization
- Cloud deployment
- Multi-language support
- AI meeting summaries
- Mobile application
- Organization analytics
- Kubernetes deployment

Do not describe future scope as completed work.

---

# 18. References

Include references only for technologies, frameworks, libraries, and official documentation actually used in the project.

Examples:

- Faster-Whisper
- FastAPI
- React
- PostgreSQL
- Hugging Face
- SQLAlchemy
- PyTorch

Avoid citing unrelated sources.

---

# 19. Quality Checklist

Before finalizing the presentation, verify the following:

✓ Maximum 15 slides

✓ Uses official university template

✓ Based only on approved project documentation

✓ No fabricated features

✓ No fabricated technologies

✓ No fabricated metrics

✓ One-month project narrative maintained

✓ Logical storytelling

✓ Technical accuracy preserved

✓ One primary visual per slide

✓ Concise bullet points

✓ Speaker notes included

✓ Design notes included

✓ Academic tone maintained

✓ Professional appearance

✓ Ready for faculty evaluation

---

# 20. Final Instruction to the AI

When generating the presentation:

1. Think about the entire presentation before generating individual slides.
2. Optimize content distribution across all slides.
3. Eliminate redundant information.
4. Merge related topics whenever appropriate.
5. Prioritize clarity over quantity.
6. Preserve technical accuracy.
7. Follow the university template exactly.
8. Never hallucinate missing information.
9. Maintain the one-month implementation narrative.
10. Produce a presentation that is polished, professional, and immediately ready for academic delivery.
